# 板子 ↔ Hermes 适配性研究（M5）

前提：**这块板是 9 哥 与 Hermes 之间的通道**，不是卫星音箱（ROADMAP 开头）。
输入：M3 的能力矩阵（`docs/device-capabilities.md`）、M4 的真机行为（ROADMAP M4）。

---

## 1. 先把延迟拆成两种，不然会优化错东西

9 哥 2026-10-27 定的口径：

| 类别 | 定义 | 现状（真机实测） | 目标 |
|---|---|---|---|
| **对话延迟** | 说完一句话 → 第一个字出声，且这一轮不涉及工具 | **3.13 s**（Hermes 直连）；DeepSeek 对照 0.77–0.83 s | 越低越好；至少不能比打字聊天更难受。建议 ≤1.5 s |
| **工具延迟** | 派一件事 → 工具跑完 → 结果回来 | HA 查询一轮 **11.46 s**（其中 LLM 10.8 s 含多次工具往返） | **不作为对话指标**——工具在后台跑，不占我们说话的界面。但**开口不能沉默**：≤1.8 s 必须先出声 |

这条区分决定 M6 的施工顺序：先解决「对话时开口快」和「派活时先应一声」，
而不是去压工具本身的耗时。

**实测明细**（同一块板、同一晚）：

```
纯聊天   [asr]0.12 + [llm]2.33 + [tts]0.68 → 首帧 3.13 s
派活(HA) [asr]0.09 + [llm]10.82 + [tts]0.55 → 首帧 11.46 s
打字对照 同一条 HA 请求走 Hermes API 会话 10.7 s
```

## 2. 两侧清单

**Hermes 侧（agent 能力）**：记忆、工具调用、技能、子 agent 委派、定时任务、
审批、文件与图像、通知（Telegram）、多模型路由。

**板子侧（通道）**：麦克风（16 kHz Opus，唤醒在设备端）、喇叭（音量 60，纯播放）、
屏（480×320，能显示 PNG）、摄像头（GC2145，VGA JPEG → 经我们的 vision 端点）、
BOOT 按键、触摸（FT6336，**没有 MCP 接口**）。

---

## 3. 三态表

判定标准只有一条：**能不能从这条通道用起来**，而不是「理论上存在」。

| Hermes 能力 | 通道 | 状态 | 依据 / 缺什么 |
|---|---|---|---|
| 记忆 | 语音 | **直接可用** | M4 实测：能说出项目里程碑与正在改的文件 |
| 工具调用（agent 自己的） | 语音 | **直接可用** | M4：语音问书房灯状态，agent 自行查询后作答 |
| 设备工具（拍照/音量/亮度/翻转） | 语音 | **需转接** | 现在跑在我们自己的 tool loop 里，Hermes 看不见这些工具。要么把它做成 MCP server 给 Hermes，要么维持双工具面（见 §5-d） |
| 子 agent 委派 | 语音 | **需转接** | 派得出去，但**结果回不来**：设备空闲会关 WS，没有「主动播报」通道 |
| 定时任务 | 语音 | **需转接** | 同上：cron 到点要说话，设备可能已经断线 |
| 审批 / 二次确认 | 语音 | **可用（已实现）** | 闸口在 `call_device_tool`：先口头问，pending 120 s，说“确认”才执行。触摸那条路仍不通，也不需要 |
| 文件 / 图像（agent → 我） | 屏 | **部分可用** | 屏只吃 PNG（`preview_image`），且要先上传到可访问 URL |
| 我 → agent 的视觉 | 摄像头 | **直接可用** | `take_photo` + vision 端点，已在 M1/M3 实测 |
| 通知 | 语音 | **需转接** | Telegram 现成；要在这条通道播报，得先解决「没唤醒怎么说话」 |
| 多 agent 切换 | 语音 | **需转接** | 现在是单后端单会话；切换要有路由与会话隔离（M4 已验证隔离本身可行） |

## 4. 缺口清单（按 6 条通道质量指标）

| # | 指标 | 现状 | 缺什么 | 代价 |
|---|---|---|---|---|
| 1 | 一句能不能听清 | ASR 0.05–0.12 s，但 TTS 自测时出现「书房灯→黄灯」 | 唤醒尾巴、口音鲁棒性；可用设备端 AEC 已开 | 小（调 VAD/端点，不必换模型） |
| 2 | 什么时候出声 | 聊天 3.13 s；派活 11.46 s 沉默 | **filler**（到点先说「我查一下」）+ 聊天走快通道 | 小（filler 半天；路由一天） |
| 3 | 能不能插话 | 半双工：`if self.speaking: return` 丢了播放期音频 | 删这行 + 单点打断判据（抄 LX06 的参数） | 中（1–2 天，含真机调阈值） |
| 4 | 说完能不能接着聊 | 设备空闲会关 WS，每句都要重新喊唤醒词 | 会话保持 / 服务端 KWS 常开 | 中（涉及设备状态机，先做「延长空闲」验证） |
| 5 | 我能不能看到它看到的 | 拍照可用；屏幕截图可回传 | 随问随拍已通；连续取帧没有 | 小（按需触发即可，不做视频流） |
| 6 | 任务结果回到这条通道 | 结果只在发起的那一轮里 | 主动播报通道（保持连接或到点重连唤醒） | 大（设备协议 + 服务端调度） |

## 5. M6 施工顺序（按 ROI 排，不是按难度）

**a. filler（立即应答）** —— 半天的活，把「派活沉默 11 s」变成「1.8 s 出声 + 结果再播」。
这是 9 哥 这条口径下收益最大的一步，先做。

**b. 删掉播放期丢帧 + 打断判据** —— 全双工的地基。上游本来就在 realtime 模式推麦，
我们只是把帧丢了；判据抄 LX06（单点检测、双讲 35%、preroll 0.5 s）。

**c. 流式 TTS（按句推流）** —— 长回答（这次实测 10.87 s 音频）现在要等整段合成；
按句推可以把「开口时间」和「总时长」解耦。

**d. 设备工具 MCP 化** —— 把 `take_photo / set_volume / set_brightness / flip_camera`
做成 MCP server 暴露给 Hermes，消灭「双工具面」。做完之后 Hermes 说「我看一眼」就能直接拍照。

**e. 主动播报通道** —— 让 agent 能在没唤醒时说话（任务完成、定时提醒）。
需要设备保持连接或服务端唤起；这是「任务结果回到这条通道」的硬前提。

**f. 审批降级方案（已完成）** —— 语音二次确认落地在 `call_device_tool`，
实测 `[confirm] asking` → 确认 → `[confirm] approved`；具体的破坏性动作清单在
`config.yaml safety.confirm_tools`（reboot / upgrade_firmware / set_download_url /
reconfigure_wifi）。原始想法：
不要等触摸 MCP（那要改固件）。

**g. 双通道路由（对话延迟）** —— 闲聊走 DeepSeek（0.8 s），任务走 Hermes（3 s+），
路由判据用「是否涉及记忆/任务/设备」。放在最后，因为 filler 已经解决了「难受」的部分。

---

## 6. 结论

1. **这条通道现在已经能用**：记忆、工具、拍照、隔离都通了；差的不是能力，是**体感**。
2. **最该先做的是 filler**，不是流式、不是打断——它用半天把最刺眼的 11 秒沉默消掉。
3. **设备工具要 MCP 化**，否则 Hermes 永远不会自己拍照，只能靠我们旁路触发。
4. **审批不要等触摸**：语音二次确认就够，触摸那条路要改固件，收益不匹配。
5. HA 不投入（9 哥 明确），但它作为「工具类任务」的样本继续用来量延迟。
